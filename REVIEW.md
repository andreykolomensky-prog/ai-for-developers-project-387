# Критерии ревью

Файл для независимого ревьюера pull request. Автор изменения и ревьюер работают в разных запусках: ревьюер читает, сверяет и пишет замечания, код не правит. Решение о мерже принимает человек.

## С чем сверять

1. Прочитайте `AGENTS.md`, `GLOSSARY.md` и записи в `docs/adr/` по затронутой теме.
2. По ссылкам из описания PR откройте исходное обращение, спецификацию, тикеты и комментарий с согласованием человека. Если ссылки нет или она недоступна, это замечание.
3. Сверьте diff со спецификацией: реализовано согласованное поведение, не меньше и не больше. Изменение вне согласованного объёма отмечайте отдельно.
4. Сверьте разделы PR «Проверки», «Риск» и «Способ отката» с фактами: результаты должны относиться к текущему head SHA, а глубина проверки соответствовать последствиям ошибки.

## Правила календаря

Изменение не должно нарушать правила, на которых держится запись. Проверяйте те из них, которые затрагивает diff.

- Занятое время. Две записи не пересекаются даже частично и даже для разных типов встреч. Занятый слот не показывается свободным, запись на него отклоняется с `409`. Встреча может начинаться в момент окончания предыдущей.
- Правила на сервере. Проверки занятости, окна записи и данных гостя выполняет сервер. Проверка только в интерфейсе обходится прямым запросом в API.
- Слот из окна записи. Запись принимается только на начало слота из 14 дней окна записи, в рабочие часы владельца, и только если слот ещё не начался.
- Отклонённый запрос ничего не меняет. Запрос с ошибкой данных не создаёт запись и не занимает слот.
- Контракт. API меняется с `api/main.tsp`, каталоги `api/generated/`, `web/src/api/generated/` и `server/generated/` получены генерацией, а не правкой руками. Ответы сервера соответствуют контракту по кодам и полям.
- SDK. Интерфейс обращается к API через сгенерированный SDK, без прямого `fetch`.
- Необязательные поля. Запись без необязательного поля работает как раньше, в ответе нет `null` и пустых строк вместо отсутствующего значения.
- Данные гостя. Имя, email, телефон и заметка выводятся как текст и показываются только гостю в подтверждении и владельцу в списке встреч.
- Тесты. Новое поведение покрыто на согласованных границах: API запущенного сервера и браузерный сценарий с настоящим сервером. Тест проверяет внешнее поведение и падает, если правило нарушить.

## Что считать отдельным риском

- Изменение прав, событий, секретов или фильтров в `.github/workflows/`. Такое изменение требует отдельного решения человека, даже если diff маленький.
- Изменение правил занятости, окна записи или расчёта слотов.
- Удаление или ослабление существующих тестов.

## Формат результата

- Каждое замечание содержит файл и строку, условия, при которых проявляется ошибка, и её последствие для гостя или владельца.
- Дефекты этого изменения отделяйте от проблем, которые существовали до него.
- То, что проверить не удалось, перечислите отдельно: недоступные ссылки, отсутствующие результаты CI для текущего SHA, непроверенные предположения.
- Если подтверждённых дефектов нет, напишите об этом прямо.
- Форматирование и стиль проверяет линтер, его вывод не повторяйте.

## Повторное ревью

Прочитайте предыдущие замечания и ответы на них. Проверяйте новые правки и поведение, которое они затрагивают. Уже разобранное замечание не повторяйте без нового доказательства.
